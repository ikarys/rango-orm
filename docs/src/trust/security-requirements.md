# Security requirements

Every security claim Rango makes, and the test or check that proves it. Rango is written with AI assistance (see [How Rango is built](./how-rango-is-built.md)); the trust comes from checks you can re-run, not from this page. To report a vulnerability, see [`SECURITY.md`](https://github.com/ikarys/rango-orm/blob/main/SECURITY.md).

## Threat model

**Trusted** (the developer writes it):

- models, `#[field(default = "...")]`, `CheckConstraint` SQL and partial-unique conditions
- SQL passed to `raw*`
- migration files

**Not trusted:**

- end-user input reaching filter values and string column names
- dump files given to `restore` / `import`, and names read from the database catalog
- the network between the application and the database

**Not protected:**

- anything built into trusted SQL from user input (`raw*`, constraint SQL, field defaults)
- `rango_orm_core::Filter::raw_where`: a hidden, low-level API that takes SQL; never feed it user input
- a compromised developer machine, database server, or a dependency flaw not yet in the advisory database
- denial of service through expensive but valid queries (the default 1000-row cap and `statement_timeout_ms` limit the damage; they are not a defence)
- TLS to a local host: localhost is not forced onto TLS, and an explicit `sslmode` / `ssl-mode` always wins

## Notes

- Only SQLite asserts the error and span claims directly. PostgreSQL and MySQL map errors through the same `db_err` shape and open the same `db.query` span; there is no separate test per backend.
- Database tests under `rango-tests` are `#[ignore]`d unless the matching `integration*` feature is on (`just test-sqlite`, `just test-postgres`, `just test-mysql`).
- Claims marked "Not covered by a test" hold by construction or by CI policy; they are listed so nobody mistakes them for tested.
- `rango-bench` is an unpublished benchmark harness with no crate root, so it carries no `forbid(unsafe_code)`.
